TileInfer — Architecture Draft

A single-GPU, single-client LLM inference engine in Julia. Every hot kernel is written in cuTile.jl. The goal is to learn how the engine works, so the code favours being clear and easy to instrument over supporting many features.

Status (2026-10-30): M0–M7 done, and the first M8 fusions. M7 (speculative decoding): verifier (greedy and sampled), n-gram, draft-model and DFlash proposers, --speculate / --draft / --dflash and bench/speculative.jl; adaptive k is a later option. An EAGLE-3 proposer was built and removed on 2026-11-01: DFlash beat it on every prompt (see Performance). Target hardware: RTX 4080 SUPER (Ada, sm_89, 16 GB). Benchmarked on Qwen3-0.6B and Qwen3-4B. External documentation and papers are listed in References.

1. Design principles

  1. Copy vLLM's and DeepInfer's structure, not their size. Keep the layers they have (engine → scheduler → model runner → model → kernels) and leave out distributed execution, the multi-tenant scheduler and the request queues.
  2. Plain Julia structs, no NN framework. We never need autodiff. A model is a struct of CuArrays plus an explicit forward!. This makes every tensor allocation, layout and kernel launch visible.
  3. Kernels behind a narrow interface. Each op (rmsnorm!, rope!, linear!, attention_prefill!, attention_decode!, …) has a reference implementation (CPU / cuBLAS / broadcast) and a cuTile implementation. Both are selected by a backend type parameter, so every new kernel is correctness-tested against the reference and benchmarked from day one.
  4. Element type as a type parameter everywhere (DecoderLM{T}, PagedKVCache{T}). Only BF16 is supported early on, but FP16/FP32 (and quantized types later) only need a recompile of the kernels.
  5. No allocations in the decode loop. Buffers are preallocated, so the decode step can be captured in a CUDA graph.

DeepInfer's step() has the same shape we want: schedule → (copy/clone KV blocks) → execute_model_step → sample → post_process. It also overlaps CPU scheduling of step n+1 with GPU execution of step n ("async scheduling"). With one client and CUDA graphs this matters less, but the overlap is worth adding later. The released DeepInfer is Blackwell- and multi-GPU-oriented, and its KV-cache system is not included in the release. Use vLLM as the reference for the paged KV design.

4. Data layout conventions (Julia is column-major)

Julia arrays are column-major and PyTorch tensors are row-major. If we reverse every shape, the memory stays identical, so that is the convention here (it is also what cuTile.jl's FMHA example does):

TensorPyTorch (row-major)TileInfer (column-major)
hidden states(tokens, hidden)(hidden, tokens)
Q(tokens, heads, d)(d, heads, tokens) or (d, tokens, heads) per kernel
Linear weight(out, in)(in, out) → y = Wᵀ x
Paged K/V cache(pages, page, kvh, d)(d, page, kvh, pages) per layer
Block table(seqs, max_pages)(max_pages, seqs) Int32
  • Weights load without a transpose copy. SafeTensors.jl 1.3 memory-maps the file and returns a PermutedDimsArray over the row-major buffer. parent() of it is exactly the (in, out) column-major array, so it can go straight into a CuArray (in BF16 via BFloat16s.jl).
  • Put the reduction dimension first (contiguous) for GEMM/GEMV.
  • One K and one V pool per layer, CuArray{T,4} of shape (head_dim, PAGE, n_kv_heads, n_pages), with PAGE = attention TILE_N (64 or 128). A KV tile is then exactly one page, and a ct.load with a runtime page index is a single dense, aligned tile load.

5. Model

One generic DecoderLM{T} covers the Llama-style family. Per-family differences are config flags:

Apertus (swiss-ai) uses xIELU, an activation with learned scalars per layer (up → xIELU → down, no gate projection). Apertus 1.5 is multimodal, so only its decoder is loaded: the decoder settings are nested under text_config, its tensors sit under model.language_model., and the embedding rows past the 131,072 text tokens (image and audio codes) are skipped. pull leaves out the image and audio tokenizer shards. Its tokenizer has 136k added tokens and a normalizer that rewrites reasoning markers. The 8B needs 16.1 GB in BFloat16, so it runs with weight-only INT8 (--int8, 8.6 GB, 80 tok/s; see Performance). Correctness is checked on a tiny random Apertus and, when the 8B is pulled, against transformers' Float32 run of it on the CPU (scripts/gen_apertus_fixtures.py).

Suggested targets on 16 GB in BF16: Qwen3-0.6B / 1.7B / 4B, and Llama-3.2-1B / 3B. For speculative decoding: Qwen3-4B target with Qwen3-0.6B draft (same tokenizer, about 9.5 GB combined, which leaves room for the KV cache).

Forward pass for one step (T = tokens in this step):

x = embed[ids]                                  # gather          (H, T)
for layer in layers
    h = rmsnorm(x)                              # fused add+norm after layer 0
    qkv = linear(h, Wqkv)                       # one fused projection
    q, k = rope(q, k, positions)  (+ q/k norm)  # fused
    kv_write!(cache, k, v, slot_mapping)        # scatter into pages
    o = attention(q, cache, metadata)           # prefill | decode | verify
    x = x + linear(o, Wo)
    h = rmsnorm(x)
    x = x + linear(swiglu(linear(h, Wgate_up)), Wdown)
logits = linear(rmsnorm(x)[:, last_positions], Wlm)

The checkpoint's separate q_proj, k_proj, v_proj and gate_proj, up_proj weights are concatenated once at load time (as vLLM does), so there are fewer, larger GEMMs.

6. KV cache & block manager

  • At startup, measure free memory after loading weights and allocating activations. Allocate n_pages for a configured fraction of what remains (vLLM's gpu_memory_utilization).
  • BlockManager: a free list of page ids, and for each sequence a block table (Vector{Int32}, mirrored into a device CuMatrix{Int32}) plus seq_len.
  • slot_mapping (token → (page, offset)) is computed on the host per step, uploaded into a static device buffer, and consumed by kv_write!.
  • Truncating is free. Rolling back a sequence (rejected speculative tokens, or a regenerate in chat) only decrements seq_len and returns surplus pages. No data is moved.
  • Prefix reuse in chat (M3): a ChatSession keeps one sequence alive, re-renders the conversation each turn, truncates the sequence to the longest token prefix it shares with the new prompt, and prefills only the rest. Templates that rewrite history (Qwen3 drops earlier <think> blocks) shorten the reusable prefix to the start of the previous reply; that is the model's training format, so it is followed.
  • Later: prefix caching across sequences (hash full pages of the token prefix, refcount pages), once several sequences share the pool.

Even with a single sequence, paging pays off: chat sessions can grow without reallocation, rollback is trivial, prefix caching becomes possible, and the attention kernels are the real thing. "Batch" in the kernels is always ≥ 1 (target + draft, or later several sequences), so we never bake in a batch size of 1.

Attention: one kernel family, three uses

The attention variants differ in the number of query rows per sequence:

  • chunked prefill: M = chunk (e.g. 512) against past pages plus the current chunk
  • decode: M = 1
  • spec verify: M = k + 1 against past pages, with a causal mask among the k+1 tokens

So the core is one paged FlashAttention kernel, with the KV loop walking the block table:

for j in 0:n_pages-1
    page = block_table[j + 1, seq]                       # scalar load
    k = ct.load(Kc; index=(1, 1, kvh, page), shape=(D, PAGE, 1, 1))
    ...online softmax, muladd(v, p, acc)...
end

With Tile IR ≥ 13.3, sparse views (@view Kc[:, :, kvh, page_tile]) gather several pages in one load. Measure both.

When M is small (decode/verify), a 128-row Q tile is mostly empty. Two fixes:

  • GQA packing: put the group_size × (k+1) query rows that share a KV head into the M dimension of one tile (Qwen3-4B: 32 Q / 8 KV heads → 4 rows per token).
  • Split-KV (flash-decoding): grid over (kv_heads, splits), write partial (acc, m, l) in FP32, then run a small combine kernel. This is needed to fill 80 SMs at batch 1. Use an FP32 workspace: BF16 atomic add needs sm_90.

Ada-specific constraints (from cuTile.jl compatibility docs)

  • Tile IR on sm_89 needs bytecode ≥ v13.2. cuTile.jl 1.0 targets v13.1–13.4. Driver ≥ 580 (this machine: 615).
  • Supported element types: BF16/FP16/TF32/FP32. No FP8 in Tile IR on Ada, even though the hardware has it, so quantization would mean INT8 or weight-only schemes.
  • No TMA, wgmma or thread-block clusters (num_cta_in_cga = 1), and no programmatic dependent launch. Kernels compile to mma.sync-style code, so tile-size tuning and the latency hints matter most.
  • The 4080 SUPER has about 736 GB/s of memory bandwidth, so the decode roofline ≈ 736 GB/s ÷ weight bytes: about 90 tok/s for Qwen3-4B in BF16 and about 580 tok/s for 0.6B. These are the numbers to aim for.

8. Speculative decoding

Build it in stages. Each stage reuses the verifier.

  1. Verifier + rejection sampler (model-agnostic): run the target on [last_token, d1..dk] (M = k+1 per sequence, paged causal attention), accept the longest valid prefix (greedy match, or Leviathan/Chen rejection sampling for temperature > 0: the target's own sample for deterministic drafts, the p/q rule for drafts sampled from a recorded q), sample a bonus token, and truncate the KV of rejected positions.
  2. N-gram / prompt-lookup proposer: no draft model, all on the CPU. It exercises the full verify path and is very effective on chat or code that repeats earlier context.
  3. Draft-model proposer: Qwen3-0.6B drafting for Qwen3-4B. It has its own DecoderLM and its own PagedKVCache but shares the BlockManager logic. The k draft steps form a natural CUDA graph.
  4. EAGLE-3 drafter (removed 2026-11-01, see Performance): one layer reading the residual stream of three target layers, drafts chained one token at a time like the draft model. DFlash, which reads the same kind of states, beat it on every prompt.
  5. DFlash drafter (src/engine/dflash.jl): five Qwen3 layers whose keys and values for context positions come from five target layers' states (which the target's steps keep, enable_aux!), and a block of [next token, 15 masks] attending without the causal mask (attention(…; causal = false)), so one pass drafts 15 tokens; verify steps take up to 16.
  6. Later: dynamic k based on acceptance rate (DeepInfer's scheduler adapts using measured forward/sample times).

The engine's step() becomes: propose → verify → accept → rollback → emit 1..k+1 tokens.

9. ModelRunner & CUDA graphs

Implemented in M6 (src/model/decoder.jl, src/engine/runner.jl):

  • One forward pass, written in place. run_step! runs a step entirely on the device, writing only into a StepBuffers (every activation, the logits) and the KV cache. Every op has an in-place form (rmsnorm!, linear!, …); TileBackend's allocate nothing, and RefBackend falls back to "compute, then copy", so both backends share the same layer loop. forward!(model, cache, seq, ids) is that step with buffers allocated for it.
  • Inputs on the device. The step's metadata (the vLLM InputMetadata for one sequence): token ids, 0-based positions, cache slots, and the block table zero-padded to the pool's page count (a multiple of 16, so its length never changes). prepare_step! reserves pages and uploads them with copyto! before the step (synchronous pageable copies for now; pinned async copies later). Kernels read start and positions from these buffers, never as scalar launch arguments, which a graph would freeze.
  • ModelRunner(model, cache). Steps of up to 8 tokens (decode, spec verify) keep a StepBuffers per token count. The first step of a count runs eagerly (that compiles its kernels), then is captured with CUDA.capture/instantiate; later steps upload their inputs and CUDA.launch the graph. Longer steps (prefill) run eagerly. Graphs are keyed by tokens per step only, as there is one sequence; with several sequences the key becomes (num_seqs, tokens_per_seq) buckets, as in DeepInfer's build_graph_batch_sizes. The graph holds the addresses of weights, pools and buffers, so it is valid for the runner's lifetime. generate! and ChatSession (graphs persist across turns) use it.
  • Correctness: a replayed step's logits are bit-identical to an eager step's, and a decode step allocates no GPU memory (test/engine/runner.jl).
  • Graphs remove the host cost of the ~540 launches of a decode step (≈ 5 µs each), but not their GPU-side cost: tiny kernels still take 2–3 µs each, so fusion (M8+) is what reduces the step further. Replaying the graph itself costs ~0.34 ms of host time, which overlaps with the GPU.

10. Compilation & startup latency

  • cuTile specializes on ct.Constant arguments (tile sizes, headdim, flags) and element types. It caches compiled CUBINs across sessions in Julia's object cache (the `diskcache` preference, on by default).
  • TileInfer.warmup(model) compiles every kernel specialization the model needs at load time. Do it inside a PrecompileTools workload for the Julia side.
  • CLI start time: install with Julia 1.12 Pkg apps ([apps] in Project.toml → ~/.julia/bin/tileinfer). Keep chat as a long-lived process. juliac --trim is not realistic with the GPU compiler stack.

11. CLI

tileinfer pull Qwen/Qwen3-4B [--revision main]   # *.safetensors, config, tokenizer
tileinfer ls                                     # cached models (shared with Python HF cache)
tileinfer rm Qwen/Qwen3-4B
tileinfer run Qwen/Qwen3-4B "Hello" [--max-tokens 256 --temperature 0.7 --top-k 20 --top-p 0.9 --seed 1 --thinking off --raw]
tileinfer chat Qwen/Qwen3-4B [--draft Qwen/Qwen3-0.6B | --ngram 3] [--k 4]
tileinfer bench Qwen/Qwen3-4B [--prompt-len 512 --gen 256] [--backend ref|tile]

pull = HuggingFaceApi.list_repo_files filtered to the allowed patterns, then hf_hub_download per file. This gives the same cache layout as Python's huggingface_hub and honours HF_TOKEN, HF_HOME and HF_HUB_OFFLINE.

14. Open questions / spikes

Answered by M0 (environment: Julia 1.13.3, CUDA.jl 6.3, cuTile 1.0.0, tileiras 13.3 / bytecode v13.3, driver 615):

  1. ✅ cuTile launches capture into CUDA graphs. Capture works when mixed with CUDA.jl broadcasts and cuBLAS mul!, and replays read the live contents of captured buffers (test/smoke/graphs.jl). Kernels must be compiled (launched once) before capture.
  2. ✅ Host overhead of a cuTile launch ≈ a native @cuda launch: about 5.2 vs 5.5 µs to enqueue. cuLaunchKernelEx itself is about 1.8 µs; the rest is Julia-side argument handling. Graph replay brings enqueue cost per kernel to about 0.01 µs. For tiny dependent kernels, wall time is about 5–6 µs per kernel either way, because the GPU-side launch and DRAM round trip set the floor (possibly also idle clocks). Graphs therefore matter whenever per-kernel GPU time is under ~5 µs, which is the case for norm, rope and activation kernels at batch 1. Fusion still matters even with graphs.

Still open:

  1. Paged KV loads: a runtime-indexed ct.load per page vs sparse-view gather. M5 uses one runtime-indexed load per page; sparse views (several pages per load) are not measured yet.
  2. ~~GEMV performance in cuTile at M = 1 vs cuBLAS.~~ Answered at M4: the cuTile GEMV is 1.0–1.3× cuBLAS, so decode linears have no cuBLAS fallback. M = k+1 (verify) uses the GEMM with per-shape tiles; a split-K GEMM did not beat it at n = 2…64.
