Performance log

What each milestone and each optimization bought, in BF16 on the RTX 4080 SUPER (736 GB/s): on Qwen3-0.6B up to the per-shape GEMM tiles, and on both Qwen3-0.6B and Qwen3-4B from then on (see "Two models"). Newest last. Numbers that informed a decision but did not pan out are kept, with the reason, so they are not retried blindly.

How things are measured

  • bench/run.jl (see CLAUDE.md), minimum time over samples, --seconds 2 for decisions; expect ±3–5 % between runs at the model level (the GPU also drives the desktop). Keys start with the model (Qwen3-4B/model/...) since 2026-10-29; earlier keys were 0.6B.
    • model/decode_ctx1024/<be>: one eager decode step after 1,023 cached positions, synced.
    • model/decode_graph_ctx1024/tile: the same step replayed from a CUDA graph (M6+), synced.
    • model/generate64[_unpipelined|_sampled]_ctx1024/tile: 64 tokens after 1,023 positions, per token (perf branch). Greedy pipelined overlaps host and GPU, so only it shows the gaps between steps disappearing; _sampled uses the model's recommended sampling (Qwen3: temperature 0.6, top-k 20, top-p 0.95), which is what tileinfer run/chat do.
    • model/prefill{64,512}/<be>: a 64- or 512-token prompt in one step.
  • End-to-end race (bench/ref/tileinfer_race.jl, bench/ref/vllm_race.py): 512-token prompt, 256 greedy tokens, prefill = latency of generating 1 token, decode = (256 − 1) / (latency(256) − latency(1)). Same prompt ids and the same first tokens on both engines.
  • Kernel breakdowns: CUDA.@profile trace = true over 20 generated tokens, summing kernel durations per name (the tracer adds ~5 % to wall time). Since 2026-10-29 bench/breakdown.jl does this for decode and prefill steps of both models, per kernel role.
  • Roofline for decode at 1,024 positions: Qwen3-0.6B reads 1.19 GB of weights + 117 MB of KV cache per token ≈ 1.78 ms, i.e. ~560 tok/s; Qwen3-4B 8.04 GB + 151 MB ≈ 11.1 ms, ~90 tok/s.

M4: cuTile kernels (2026-10-27)

Every op except attention moved to cuTile; attention still used the reference.

  • Decode GEMV at 68–93 % of the DRAM roofline (1.0–1.3× cuBLAS); prefill GEMM 0.70–0.92× cuBLAS; rope / rmsnorm / store_kv / embed 3–29× the reference.
  • End to end only 1.12× (decode) and 1.41× (prefill): the reference attention (≈ 1 ms per layer, ~190 kernels per layer, ~6k GPU allocations per token) dominated.

Where the remaining time is

Against the ~1.78 ms roofline at 1,024 positions:

  • GEMVs: 1.94 ms vs a 1.62 ms floor for reading the weights once. The lm_head is at 92 %; the small layer GEMVs (4–12 MB each) lose 2–3 µs each to the fill and drain of a kernel. Levers: weight-only INT8 (halves the bytes, the biggest one left), or split/stream-K and persistent kernels. Ada has no programmatic dependent launch to overlap kernel tails.
  • Attention: 0.31 ms vs ~0.16 ms for reading the KV cache. Each split handles about one page, so the kernel is latency-bound; longer contexts amortize this better.
  • Small kernels: ~0.25 ms, already fused down to 3 per layer.

End to end is the robust comparison. vLLM's 1-token latency is multimodal, with clusters at ~11, ~25 and ~40–47 ms within the same process (sorted trials of one run: 10.8, 11.0, 11.1, 11.1, 11.5, 28.4, 46.8, 47.2, 47.5, 47.9 ms), while its 256-token latency varies by under 1 ms. So the extra 15–35 ms are per-request overhead that the 256-token request does not pay in full, not prefill compute. Its fast mode (~11 ms) is the best estimate of vLLM's prefill, so the subtraction above overstates its decode speed: with 11 ms, vLLM decodes at 2.48 ms/tok (403 tok/s), as in the earlier 10-trial runs that hit the fast mode. TileInfer's timings are unimodal (prefill IQR 0.3 ms).

Earlier single runs: vLLM --eager 172 tok/s decode / 39k tok/s prefill; TileInfer M6 343 tok/s / 40k tok/s (e2e 0.755 s).

Two models in the benchmark suite (2026-10-29)

bench/run.jl now runs every op and model benchmark on Qwen3-0.6B and Qwen3-4B (one model after the other, ~7 min with --seconds 2), and adds sampled generation. Baseline saved as two-models (commit 3763805 + the suite changes). The two models stress different things: 0.6B has small layers (4–12 MB per GEMV), so per-kernel overheads and host work show; 4B has up to 100 MB per GEMV, so decode is a bandwidth test and prefill a tensor-core test. Same context (1,024 positions), same KV shape (8 KV heads of 128), so attention costs the same.

  • The M8 target (≥ 80 % of the decode roofline) is met on 4B, not on 0.6B. The fixed costs that 0.6B still pays (kernel fill and drain, host sampling, graph launch) are constant per token, so at 4B they are drowned by 5× more bytes per token.
  • Sampled decoding costs a constant ~0.7–0.9 ms per token: the logits (600 KB) are copied to the host and sampled there, step by step, with the GPU idle meanwhile. That is 36 % of a 0.6B token and 5 % of a 4B token. Device top-k/top-p sampling inside the graph, pipelined like greedy, removes it; it is also what M7's rejection sampler needs.
  • Graphs matter little at 4B (eager step 2 % slower vs 6 % at 0.6B): 363 launches cost the same host time, but the GPU takes 5× longer per step, so enqueueing keeps ahead.

Sampled drafts, the p/q rule (2026-10-30)

DraftProposer(…; sample = true) (also Eagle3Proposer, DFlashProposer; CLI --sample-drafts): when the target samples, the drafter samples its drafts with the target's parameters on its own logits, under a seed of its own, and records each draft's filtered distribution q (its ≤ 64 survivors' ids and probabilities, written by the sampling kernel itself). The verify step then runs accept_token! at each drafted position: accept d with probability min(1, p(d)/q(d)), else sample from max(p − q, 0) (a (64, 64) comparison of the two survivor lists), with a uniform stream of its own for the acceptance; the bonus position samples as before. A rejected position never emits the draft, so the host's accept loop is unchanged. The tokens follow the target's distribution, but are no longer plain decoding's. The new kernels share the candidate selection with the plain sampler (survivors, pick), which measured the same after the refactor (16.8 µs).

Greedy drafts are accepted with probability p(argmax q), sampled ones with Σ min(p, q). With Qwen3's recommended sampling (T 0.6, top-k 20, top-p 0.95) the distributions are peaked and the two are close. bench/speculative.jl --sampled [--pq], 4B target, 256 tokens; best k of each method, speedup over sampled plain decoding (greedy drafts → sampled drafts):

INT8 KV cache (2026-10-31)

PagedKVCache(model; quantize = :int8) (--kv-int8 in the CLI, --kv int8 in bench/run.jl, keys <model>-kvint8/...): each cached key or value vector (one KV head at one position) as Int8 with one Float32 scale, round to nearest, written once by the fused attention_inputs kernel (Int8Pages, src/ops/quant.jl). INT8 GEMM tiles (2026-10-31)

INT8 prefill was 8–11 % slower than BF16 although it reads half the weight bytes, and at 64 tokens, where a GEMM is bandwidth-bound, the INT8 GEMMs were 0.68–1.13× BF16. Under ncu (Qwen3-4B down): at 512 tokens 255 registers and 1.6× BF16's instructions (byte shuffles and conversions of the weight tile); at 64 tokens 29 % of DRAM peak against BF16's 90 %, with 37 % of the stall samples on the conversion waiting for its global load: the Int8 tile is not staged through shared memory and overlapped like the BF16 operands. Neither latency hints on the weight loads (1–8) nor swapping the operands (Xᵀ W, the weight in its natural layout as the B operand) helped. Tiles and occupancy did: a sweep of 15 tiles × occupancy 1, 2 on the layers of Qwen3-0.6B, Qwen3-4B and Apertus 8B at n = 8, 64, 512 found the latency-bound INT8 blocks always want two per SM, narrower tiles than BF16 at 512 tokens (128 × 64 × 64), and at ≤ 64 tokens deeper K steps (32 × 32 × 256, or 64 × 64 × 128 on large grids). gemm_int8_config encodes that: within 1.5 % of the best tile summed over the sweep (worst case 1.11×), 1.23× faster than BF16's rule. DFlash without a host round trip (2026-10-31)

A DFlash step was: drafter step, host waits for the drafts and uploads them into the verify step, verify step, host waits for the target's tokens. Now the drafter's sampling writes the drafts into a device vector (propose_on_device!), and verify!(…; drafts) copies them into the verify step's ids on the stream, after the upload of its other inputs: the host enqueues both steps back to back and waits once, after the verify step. The second wait remains: the host needs the accepted count to truncate the cache and to pick the next drafter graph (one per context length). The drafter's 15 per-position sampling calls (30 launches) became one batched sample_tokens! (three launches: candidates over a (chunk, column) grid, one block per column sampling with counter c + j − 1, and a one-block kernel advancing the counter, which no block of the sampling kernel may do while others read it); same tokens and distributions as the per-column calls.

Under the tracer (Qwen3-4B, k = 15, "explain"): GPU idle time inside generation fell 2.8×, sampling 0.086 → 0.050 ms per step. End to end (bench/speculative.jl, greedy, same tokens and steps before and after):
