# TileInfer

A single-GPU LLM inference engine in Julia, built to learn how engines work.
Hot kernels are written in cuTile.jl. Clear, measurable code wins over feature breadth.

- Design and roadmap: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Check which milestone is current before adding features.
- External docs, papers and local package-source paths: [docs/REFERENCES.md](docs/REFERENCES.md).
  For cuTile questions, read `pkgdir(cuTile)/docs/src/man/` and `examples/` before searching the web.

## Commands

```sh
julia --project=test test/runtests.jl                 # full suite, ~130 s (cuTile examples, model loads)
julia --project=test test/runtests.jl kernels graphs  # only files whose path contains an arg, ~10 s
julia --project=test test/coverage.jl [--uncovered] [filters]  # local line coverage of src/, ~95 s
julia --project=bench bench/run.jl [--filter RE] [--save NAME] [--compare NAME] [--model REPO,...]  # op + model benchmarks
julia --project=bench bench/breakdown.jl [--model REPO,...] [--filter RE]  # GPU time per kernel of real steps, ~2 min
julia --project=bench bench/speculative.jl [--model REPO] [--draft REPO|none] [--k 2,4,7] [--sampled]  # spec decoding on chat prompts, ~4 min
ncu --profile-from-start off --set full -c 1 -o bench/results/NAME \
    julia --project=bench bench/profile.jl --model Qwen/Qwen3-0.6B Qwen3-0.6B/ops/linear_down/decode/tile  # one kernel under Nsight Compute
python3 bench/ncu_summary.py bench/results/NAME.ncu-repz [--compare OLD.ncu-repz]  # compact report
```

Profiling workflow, model-step costs and how to read the summary: [docs/PROFILING.md](docs/PROFILING.md).
What each milestone and optimization gained, including what did not pan out: [docs/PERFORMANCE.md](docs/PERFORMANCE.md).
To tune a kernel, profile it before and after a change and read `ncu_summary.py --compare`
rather than raw `ncu` output (`ncu` is in /usr/local/NVIDIA-Nsight-Compute). Take timings
from bench/run.jl: `ncu` serializes kernels and locks clocks.

Benchmarks (bench/suite.jl): for Qwen3-0.6B and Qwen3-4B (keys start with the model,
`Qwen3-4B/ops/linear_qkv/decode/tile`), every op at the model's shapes for decode (n = 1) and
prefill (n = 64 and 512), primitive and fused (`attention_inputs`, `add_rmsnorm`,
`linear_swiglu`, `sample`, as the step calls them), plus end-to-end prefill and decode steps and 64-token generation
(greedy pipelined, greedy step by step, and with the model's recommended sampling, pipelined), for each
backend that has a method (new `TileBackend` methods are picked up automatically). The models
run one after the other (~9 min for both with `--seconds 2`); `--model` or a filter narrows
it. A kernel change must be checked on both: 0.6B is dominated by per-kernel overheads, 4B by
bandwidth (decode) and tensor-core throughput (prefill). Report columns are per call, with
GB/s and % of the 736 GB/s roofline. Op arguments rotate through copies totalling > 2× L2, so
decode GEMMs read from DRAM as in the real model. Save a baseline before changing a kernel
(`--save before`), then `--compare before`. Results live in bench/results/ (gitignored);
results saved before the model prefix existed compare as Qwen3-0.6B.
Expect ~±10 % run-to-run noise from GPU clocks; use `--seconds 2` for decisions.
Op benchmarks launch eagerly, so kernels under ~6 µs measure their launch (rmsnorm, rope,
attention inputs, decode attention), not their GPU time. For what each kernel costs inside
a real step (decode replayed from a graph), and its share of the step, use bench/breakdown.jl
(see docs/PROFILING.md); decide what to optimize from it, and measure the change with run.jl.

If `julia` is not on PATH, use `~/.juliaup/bin/julia`.
`test/` and `bench/` are workspace projects that share the root `Manifest.toml`. Add
dependencies to the project that needs them (`julia --project=test -e 'using Pkg; Pkg.add(...)'`).

Tests that need a real checkpoint use `TEST_MODEL` (Qwen/Qwen3-0.6B, `julia --project=. -m TileInfer pull Qwen/Qwen3-0.6B`)
and are skipped when it is not pulled. Golden outputs from the Hugging Face reference
implementations live in `test/fixtures/` and are generated by `scripts/gen_fixtures.py`
(`uv run scripts/gen_fixtures.py ...`; uv installs its Python deps in an isolated env),
and reference logits by `scripts/gen_model_fixtures.py` (CPU torch + transformers, ~4 min).
Regenerate them only when the corpus or the model changes; never edit them by hand.

While iterating, run the filtered tests for the files you touched. Run the full suite before
calling a milestone done. Register new test files in the `TESTS` list in `test/runtests.jl`.

## Hardware

RTX 4080 SUPER: Ada, sm_89, 80 SMs, 16 GB, ~736 GB/s. Tile IR on Ada has no FP8, no TMA,
no clusters, and no BF16 atomic add (use FP32 workspaces).

## Conventions

- **Column-major, with shapes reversed relative to PyTorch:** hidden states `(hidden, tokens)`,
  linear weights `(in, out)` with `y = Wᵀx`, paged KV `(head_dim, PAGE, kv_heads, pages)`.
  Upload safetensors weights from `parent()` of the `PermutedDimsArray` (no transpose copy).
- **Backends:** every op has a `RefBackend` method (broadcast/cuBLAS) and a `TileBackend`
  method (cuTile). A new cuTile kernel lands together with its correctness test against the
  reference and a benchmark.
- **Element type is a type parameter** (`DecoderLM{T}` …). BF16 is the default.
- **No allocations or host syncs in the decode step**, so it stays CUDA-graph capturable
  (`ModelRunner` captures steps of ≤ 8 tokens). Every op has an in-place `op!` that
  `run_step!` calls on `StepBuffers`; a new TileBackend op needs one too. Kernels read
  per-step values (positions, slots, block table) from device buffers, never as scalar
  launch arguments, which a graph would freeze. Compile kernels (launch once) before capturing.
- **No NN frameworks** (Flux/Lux). Models are plain structs of `CuArray`s.
- **Never `mul!` on BFloat16 `CuArray`s.** CUDA.jl falls back to a generic kernel that
  accumulates in BFloat16 (~30 % error at K = 1024). Use `CUBLAS.gemmEx!` (Float32
  accumulation), as `linear(::RefBackend, …)` does.
- **Numerics vs transformers:** RefBackend rounds to `T` where PyTorch does. Float32 runs
  must match the HF fixtures to ~1e-4 (that is the correctness check); BFloat16 runs differ by
  a few ulps and greedy continuations diverge at near-ties, which is expected.

## cuTile notes (learned the hard way)

- Kernels live in `src/ops/tile/`, one in-place launcher per op (`rmsnorm!(be, y, ...)`)
  with the functional op allocating the output; round to `T` where the reference does, so
  element-wise kernels are bit-identical to RefBackend (tests check that).
- No `for` loops over tuples of arrays in kernels ("Cannot resolve LoopOp init value"):
  unroll through an `@inline` helper.
- `ct.load`/`ct.store` indices are in tile units; along a size-1 tile axis that is the
  element index. `order = (2, 1)` loads a transposed tile (index/shape in permuted order).
- Kernels specialize on each array's shape divisibility and contiguity, not only on types:
  a new token count can mean a new compile. Pad arrays whose length grows during decode
  (the block table is padded to a multiple of 16 pages in `forward!`).
- Keep each launch under 32 kernel parameters. A `TileArray{T,N}` flattens to 1 + 2N (pointer,
  sizes, strides), plus 1 for the RNG seed; from 32 on, CUDA.jl's `pack_arguments` takes
  Base's untyped `map` path (~15 µs and ~430 allocations per launch). Pass 2-D views
  (`reshape(pool, head_dim, :)`) instead of 4-D arrays.
- Tiny kernels cost ~5.5 µs per launch (vs ~3.5 µs for a CUDA.jl broadcast); below that,
  only CUDA graphs help.
- The GPU also drives the desktop (compositor, browsers, …) and idles at 210 MHz: time
  kernels as the minimum over many short trials after a warm-up, never as one averaged loop.
- Tile shapes and code layout change codegen a lot, so measure every restructuring:
  identical logic moved into an `@inline` helper ran 1.7× slower, a 3-D tile reduced over
  its third axis 60× slower, and dropping a trivial size-1 axis 5× slower. Small tile
  dimensions (8 columns) also compile to slow code: pad them to 16.

## Dependency notes

- CUDA.jl is held at 6.3 because cuTile 1.0.0 caps `CUDA_Compiler_jll` at 0.5. Revisit when a
  new cuTile is released.
- TextEncodeBase/BytePairEncoding fail to precompile on Julia 1.13, so they are not used for now.
- Transformers.jl is reference code only. Do not add it as a dependency (it pins CUDA 5).
